# Skill 缺陷评估与脱敏反馈协议（低侵入 · 克制触发）

> **低侵入原则**：日常个案修改**完全静默**，绝不打断写作或自动调用 `gh` 提交。仅在用户**明确质疑/推翻 Skill 规则本身**时在回复最末附一句极短提示；用户主动要求或确认起草反馈时，执行本协议。

---

## 1. 先区分：个案修改 vs. Skill 缺陷

| 归因结论 | 判断标准 | 处理方式 |
|---|---|---|
| **个案修改（Case-Specific）** | 仅涉及当前项目的业务数值、特定字段名、临时措辞偏好或客户定制例外 | 直接告知用户属于个案调整，**不建议提 Issue**。 |
| **Skill 缺陷（Skill-Level Gap）** | 反映出指南或 Skill 规则本身的普遍性问题，其他项目也会重复踩坑 | 按下方 4 类标签归因，生成**脱敏后的 Issue 草稿**交用户审阅。 |

### 四类 Skill 缺陷标签

| 标签 | 含义 | 典型示例 |
|---|---|---|
| `incomplete` | **写得不完整 / 漏场景** | 缺少某类高频组件模板（如固定章节报告）、漏掉关键自检项 |
| `mismatch` | **不适配当前场景** | 前置假设过窄、默认流程不适用于某类常见项目形态 |
| `definition-issue` | **口径或原则有问题** | 规则方向本身有偏差（如曾误设“默认按代码改 FSD”而非双向审校） |
| `too-rigid` | **过于死板 / 过度约束** | 强制规则限制过死，导致正常业务表达或排布显得别扭 |

---

## 2. 强制脱敏红线（提 Issue 前必须逐项过滤）

开源或跨团队共享仓库的 Issue **严禁包含任何客户或内部敏感信息**：
- ❌ 剥离真实客户名、项目代号、内部产品/系统专有名（替换为 `System A` / `External Ticketing System` 等泛化词）；
- ❌ 剥离内网 IP、内部域名、飞书/文档真实 URL、Token、邮箱、人名；
- ❌ 剥离真实业务截图、真实告警样本与具体业务指标数值；
- ✅ 仅保留：**抽象后的场景描述 + 命中了哪条现有规则 + 为什么不好用 + 建议如何修订规范**。

---

## 3. 标准 Issue 草稿模板

先输出以下草稿供用户审阅；**默认绝不自动执行外网提交**，仅在用户明确指令「帮我直接提 Issue」且当前环境具备 `gh` 权限时，再执行 `gh issue create --repo Starsaddict/FSD-skill ...`：

```markdown
### 标题
[<skill-name>][<label>] <一句话概括规则问题>

### Labels
`<skill-name>`, `<incomplete | mismatch | definition-issue | too-rigid>`

### 1. 涉及位置
- Skill / 文档：`skills/<skill-name>/...`（或 `docs/fsd-guide.md`）
- 相关章节或条款：`<章节名>`

### 2. 脱敏后的触发场景
<用泛化语言描述发生了什么，禁止出现客户名、内网地址或真实数据>

### 3. 问题分析
- 归因类别：`<写得不完整 | 不适配当前场景 | 口径有问题 | 过于死板>`
- 当前规则的不足：`<具体说明哪条规则导致了什么问题>`

### 4. 建议修订方向
<给出可落地的规则修改或补充建议>
```
