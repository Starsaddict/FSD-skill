# Mode 2：研发代码仓驱动（生成 / 双向审校 FSD）操作指南

本指南专供 **Mode 2（Code-Sync Mode）** 使用，帮助研发或产品结合**实际代码仓库** + `fsd-writer` Skill 完成两类任务：
- **Mode 2a（从代码仓逆向生成 FSD 初稿）**：已有代码实现，按标准 FSD 指南产出业务可读的功能规格说明书。
- **Mode 2b（FSD vs. 代码仓双向差异审校）**：已有 FSD 与代码实现，将二者逐项比对，把规则、口径、边界上的出入完整列出来，**供研发与产品审核究竟应按 FSD 修正业务实现，还是将合理演进同步回 FSD**。

---

## 1. 核心分析方法论：「从前端到后端」

> **为什么必须先看前端、再看后端？**
> 最终用户**只接触前端，不接触后端**。用户是通过前端进入功能、阅读并理解页面内容、发起交互来完成业务目标的。因此，FSD 的主骨架必须由**前端用户接触面**决定；后端代码与规则配置的作用，是沿着前端触点向下补充用户看不见但真实支配行为的**具体规则、机制、计算口径、校验与异常处理**。

### 第一步：前端定骨架与用户旅程（用户唯一接触面）

先扫描前端代码，完全从用户视角还原“从哪进 → 看到什么 → 怎么理解 → 怎么操作”：

| 前端扫描维度 | 优先检索的代码位置 | 需提取的用户体验事实 |
|---|---|---|
| **导航与入口（Entry Path）** | 路由配置（`routes` / `router`）、侧边栏与顶部菜单组件 | 面包屑层级、默认落脚页、Tab 结构、按角色隐藏的入口 |
| **页面信息架构（Views & Layout）** | 页面组件、Metric Cards、列表/表格、分栏工作区、图表、报告展示组件 | 每个区域向用户呈现哪些核心信息、区块排列顺序、Tab 切换关系 |
| **界面文案与交互（UI & i18n）** | i18n 语言包（`en.json` / `zh.json`）、事件处理器、弹窗与空态组件 | 按钮名、列名、状态徽标、搜索/筛选/排序、行点击目标、空态/加载失败/二次确认提示语 |
| **表单控件与显隐联动（Forms）** | 表单组件、前端校验（Zod / Yup / Form Rules） | 控件类型、必填标记、默认值、级联显隐/只读条件、前端阻断提示文案 |

### 第二步：顺前端触点穿透后端与规则配置（补充规则、机制与边界）

以第一步还原出的页面与操作为索引，再追查对应的后端逻辑、状态流转与 Prompt/配置文件，补齐前端看不全的业务契约：

| 后端补充维度 | 优先检索的代码位置 | 需补充的业务规则与机制 |
|---|---|---|
| **计算公式与统计口径** | 指标聚合服务、报表统计逻辑、Prompt 报告模板 | 精确分子/分母定义、统计窗口起止、时间归属字段、分母为 0 / null 的处理（留白 vs 0）、报告固定章节 |
| **状态机与生命周期** | 枚举定义（`enum` / `constants`）、状态转换逻辑、定时任务/超时任务 | 全部合法状态、转换条件、不可逆终态、多计时器默认时长与重置条件、到期去向 |
| **业务校验与异常兜底** | 后端 Validator、业务 Service 异常分支、重试逻辑 | 后端拦截条件、失败后游标是否推进、重试资格与日志留痕、并发锁与失败降级 |
| **外部系统集成与回调** | 连接器适配层、Webhook/Callback 处理器、状态码映射表 | 外部建单/关单条件、1:1 状态映射、回调鉴权/防伪造回查/空参拒绝/读取失败降级规则 |
| **权限守卫与高危护栏** | 后端 RBAC Middleware/Policy、Reset/Delete 执行逻辑 | 工作空间隔离边界、接口级角色校验、数据清理的 `Clears`/`Keeps`/恢复行为及生产防护 |
| **Prompt / 规则配置** | 数字员工 System Prompt、Skill 规则文件、调度配置 | 写入 Prompt 的业务阈值、优先级判定标准、报告固定章节与输出约束（并注明修改即生效） |

## 2. 核心护栏：工程语言 → 业务语言转译表

> **铁律（Anti-Leak）**：后端扫描是为了补全业务规则与机制，**绝不允许将工程实现细节直接泄漏进 FSD**！必须完成如下转译：

| 代码仓中看到的工程事实 | ❌ 严禁直接写入 FSD | ✅ 必须转译成的 FSD 业务表达 |
|---|---|---|
| `table_situations.title VARCHAR(64)` | “数据库表 `situations` 的 `title` 字段为 `VARCHAR(64)`” | “**Title**：简洁标题，不超过 64 个字符” |
| `if (status === 20) return 'Completed'` | “调用 `mapDosmStatus()` 将 `dataStatus=20` 转为枚举 `COMPLETED`” | 在唯一权威状态映射表中写：`Completed \| DOSM dataStatus 20 \| 处理完成；计入已关闭工单` |
| `if (!role.includes('ADMIN')) hideSettings()` | “`useAuth().hasRole('ADMIN')` 控制齿轮组件渲染” | “右上角 **Settings** 图标仅对 **Administrator** 与 **Workspace Owner** 可见（详见 2.2.1）” |
| `Zod.number().min(1).max(1440).default(10)` | “请求体 `interval_min` 经 Zod 校验范围 `[1, 1440]`” | “**Collection interval (minutes)**：数字输入框，必填，默认 `10`，允许范围 `1–1440` 分钟” |
| `POST /api/v1/internal/triage/run` | 在 FSD 中罗列内部 REST API 路径与 JSON Schema | **不写内部 API**；改为描述业务触发条件（定时调度触发或点击某按钮触发）与可见结果 |
| `POST /api/v1/.../dosm/work-order-events`（外部需配置的回调） | 贴出完整 Controller 代码与内部签名细节 | 仅在“外部集成与回调”节写出供外部配置的业务回调地址模式 + 6 项业务安全校验规则表 |

## 3. Mode 2a：从代码仓逆向生成 FSD 初稿（分步检查点）

1. **Checkpoint 1 — 提交前端还原的目录骨架与待补信息**
   - 完成“前端定骨架 → 后端补规则”扫描后，先输出：
     - 已定位的关键前端页面/路由与关联后端规则/Prompt 文件清单
     - 按用户视角还原的 FSD 目录大纲（遵循 `structure-and-journey.md`）
     - 代码中**无法推断的业务上下文**（如业务背景痛点、客户占位参数确认责任人、代码里的临时兜底逻辑），请用户补充或标 `[Open Check]`
   - **停下等用户确认大纲与目标语言**，再动笔。
2. **Checkpoint 2 — 逐 Feature 按组件模板生成正文**
   - 严格套用 `component-templates.md` 与 `placeholder-protocol.md`。
   - 对代码中的未完成占位或 TODO 显式标注 `*[Open Check: 代码当前为占位实现，需确认最终业务口径]*`。
3. **Checkpoint 3 — 出厂自检**
   - 运行 `qa-checklist.md`，重点复核是否存在工程术语、DB 表名或内部 API 泄漏。

## 4. Mode 2b：FSD vs. 代码仓双向差异审校协议

> **核心立场：FSD 往往代表业务意图与客户契约，不应默认“按代码去改 FSD”！**
> 当 FSD 与代码出现规则性、口径性或安全护栏上的出入时，**优先将其清晰列出，供研发审核是否应当依据 FSD 来修正业务实现**，绝不静默迁就代码改写 FSD。

### 输出标准：`FSD vs. Code` 双向差异审校报告

对每一处核对出的不一致，按以下表格呈现：

| # | FSD 章节 | FSD 约定（业务意图） | 代码实际实现（前端/后端文件路径） | 差异类别 | 建议处置方向 |
|---|---|---|---|---|---|
| 1 | `2.1.2` Metric Cards | 分母为 0 时留白，不以 0 误导 | 后端返回 `0%`（`metrics.ts`） | **规则 / 口径出入** | `[Review for Dev Fix]` 建议研发审核按 FSD 修正业务实现 |
| 2 | `2.2.4` Reset data | 生产环境需禁用或双人审批+审计日志 | 仅前端二次确认弹窗，无生产拦截（`ResetModal.tsx`） | **安全护栏缺失** | `[Review for Dev Fix]` 建议研发按 FSD 补齐生产保护 |
| 3 | `2.1.3` Alert list | 列表搜索框占位文案写作 “Search alerts” | 前端实际文案为 “Search title or alert ID”（`AlertList.tsx`） | **交互 / 文案细节** | `[Candidate for FSD Update]` 确认后可同步至 FSD |
| 4 | `2.1.3.2` 工单状态 | 列出 `Requested / Accepted` | 实际映射 DOSM `Unclaimed / In progress`（`status_mapper.ts`） | **跨系统枚举冲突** | `[Open Check]` 需产品与研发共同确认权威口径 |

### 三类建议处置标签（严格区分权重）
1. **`[Review for Dev Fix]`（默认优先用于规则 / 口径 / 边界 / 安全出入）**：代码行为与 FSD 明确的业务规则、计算口径、生命周期或安全要求存在偏差，列出供研发团队审核，判断是否应**依据 FSD 修正代码实现**。
2. **`[Candidate for FSD Update]`（仅限已确认的文案/细节补全）**：前端界面文案微调、不影响业务规则的交互补充、或 FSD 原稿遗漏但与产品意图一致的细节，经用户确认后可同步更新 FSD。
3. **`[Open Check]`（意图存疑）**：无法单凭文档或代码判定最终权威口径，交由产品/BA 与研发评审拍板。

### 审校后的双轨产出（严禁越权改文档）
1. **等待人工逐项批复**每一条差异的最终裁决；
2. 仅对用户明确批复“同步更新文档”的条目修改 FSD（并在修订记录中注明）；
3. 将所有裁定需按 FSD 修正代码的条目，单独汇总输出一份 **`研发待修复业务偏差清单（Dev Action Items）`**，方便研发直接建单跟进。
