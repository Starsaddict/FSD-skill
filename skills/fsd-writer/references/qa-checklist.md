# Mode 3：FSD 分级质检清单（QA Checklist）

本清单沉淀自真实企业级 FSD 评审过程（含客户/BA 评审意见与作者多轮自查复盘），用于 **Mode 3（QA / Review Mode）** 对已有 FSD 做全面体检，或作为起草/精修完成后的出厂自检。

---

## 严重度分级标准

- **P0（阻断级 — 必须修复）**：存在逻辑矛盾、口径冲突、高危操作缺护栏或语言混杂，直接导致研发误实现或客户评审打回。
- **P1（重要级 — 强烈建议修复）**：缺失关键定位/用途说明、边界条件模糊、结构割裂或混入开发设计项，显著降低可读性与评审效率。
- **P2（规范级 — 提升交付品质）**：排版、图注、目录同步、措辞逻辑、画幅清晰度等细节打磨项。

---

## P0 — 阻断级检查项

| 编号 | 检查项 | 判定标准（不满足即报错） |
|---|---|---|
| **P0-1** | **跨页 / 跨系统状态枚举唯一性** | 列表页、详情页、Dashboard 与外部系统状态码必须共用**同一套权威状态定义**；严禁同一概念在 A 节叫 `Requested/Accepted`、在 B 节叫 `Unclaimed/In progress`。 |
| **P0-2** | **跨系统联动与生命周期闭环** | 若本地对象关联外部工单/流程，必须明确区分**超时过期**、**人工关闭**、**规则关闭**、**合并清空**各自对外部对象的影响，以及外部关闭失败或外部被删除时的降级行为。 |
| **P0-3** | **破坏性操作生产护栏** | 凡涉及数据重置（Reset）、批量清空、不可逆删除的功能，必须写清 `Clears`（清理范围）、`Keeps`（保留范围）、恢复行为、二次确认，以及**生产环境安全保护**（禁用 / 预导出 / 双人审批 / 审计日志，未定则标 `[Open Check]`）。 |
| **P0-4** | **指标公式、时间窗口与空值口径** | 所有 Metric Cards 与图表必须给出精确公式、统计窗口起止、样本归属时间戳（如按认领时间还是发生时间）、以及**分母为 0 或无数据时的处理（默认留白，不以 0 误导）**；测试占位基线值必须标明可配置性与确认责任人。 |
| **P0-5** | **图文语言 100% 一致** | 全英文 FSD 严禁混入中文截图、中文 UI 标签或中文图表文字；全中文 FSD 同理（除明确保留的专有产品名/原文引用外）。 |
| **P0-6** | **外部回调安全校验（若涉及回调）** | 外部回调必须写清调用方鉴权、防伪造状态回查（不盲信回调体状态）、工作空间/归属匹配、非法入参拒绝、回查失败降级与最小更新字段范围。 |

---

## P1 — 重要级检查项

| 编号 | 检查项 | 判定标准（不满足即报错） |
|---|---|---|
| **P1-1** | **Purpose 先行（做什么用，不只是有什么）** | 每个页面、工作区 Zone、Detail Tab 开头必须先一句话说清“让用户来看/做什么”，严禁只罗列字段列表却不解释用途。 |
| **P1-2** | **Entry Path 与相邻视图边界清晰** | 每个主功能页与二级详情页/抽屉都必须明确“从哪里点击进入”，并说明与相似视图的定位边界（避免读者看懵“这是哪个页面、和隔壁历史记录有什么区别”）。 |
| **P1-3** | **多卡片 / 多字段拆表说明** | 3 张及以上 Metric Cards 或多字段表单/列表必须逐项拆开成统一规格表，严禁压缩成一段自然语言。 |
| **P1-4** | **表单、工作区与报告符合标准结构** | 表单遵循“顶部状态与原型图 → `Field \| Description & Constraints \| Example / Note（可选）` → 交互与校验”三段式；分栏/多 Tab 工作区遵循 4 步结构且**操作随区走**（不把主区操作流放到文末）；报告类功能必须给出**固定章节规格表**（每章固定讲什么）、统计完整性底线及已保存报告追问不可改写原则。 |
| **P1-5** | **边界条件与责任归属不留黑盒** | 定时频率（或可配置说明）、超时失效记录的查看人/是否通知、证据不足时的默认兜底策略、外部请求人身份（避免用个人管理员名污染审计日志）等关键边界不得含糊带过。 |
| **P1-6** | **Just-in-Time 落位与无重复章节** | 阶段拆解表只在 `2.1 User Journey` 出现一次（不在 `1.1 Scope` 重复）；Access Control & User Roles 放在功能讲解之后的 `2.2 Configuration`；Digital Employees 等业务参与体在所属业务总览开头集中讲一次，后文不重复拆写。 |
| **P1-7** | **无 Anti-Scope 工程 / 测试内容越界** | 严禁出现数据库表名/物理字段长度、代码类名/扩展点钩子、内部微服务 API 契约、数据迁移脚本、底层数仓模型或 QA Test Cases。 |

## P2 — 规范与品质级检查项

| 编号 | 检查项 | 判定标准（不满足即提示） |
|---|---|---|
| **P2-1** | **目录与正文 100% 同步** | `Contents` 表中列出的所有章节号与标题必须与正文完全一致，无空壳章节。 |
| **P2-2** | **术语统一** | 统计卡片统一称为 **Metric Cards**；同对象名称、按钮文案、状态词全文拼写与大小写保持一致。 |
| **P2-3** | **视觉图清晰度与纯净度** | 界面图/Sketch 视口宽度合理无横向截断、无卡在半路的滚动动画/脏测试数据、图注规范且与正文示例值一致。 |
| **P2-4** | **Placeholder 与 Open Check 收口** | 交付终稿中不得残留未替换的 `[VISUAL-PLACEHOLDER` 高亮块；所有尚未拍板的业务决策必须显式标出 `*[Open Check: ...]*` 并汇总给评审人。 |
| **P2-5** | **句式与标点逻辑通顺** | 冒号前后逻辑成立（前面是总结性短语，后面是对应的解释说明）；翻译/措辞自然准确，无歧义指代（如明确指出“保存在哪个会话”而非笼统说“报表会话”）。 |

---

## 质检报告输出模板

运行 Mode 3 时，必须按以下结构输出报告，并在文末**停下等待用户确认要修复哪些项**：

```markdown
# FSD 质检报告：《{文档标题}》

## 1. 总体健康度摘要
- **P0（阻断级）**：`{X}` 项
- **P1（重要级）**：`{Y}` 项
- **P2（规范级）**：`{Z}` 项
- **残留 Placeholder**：`{M}` 处 | **待拍板 Open Check**：`{N}` 处

## 2. 问题明细与修改建议

| 级别 | 条款 | 所在章节 / 位置 | 问题描述 | 可直接落地的修改建议 |
|---|---|---|---|---|
| P0 | P0-1 | `2.1.3.2` vs `2.1.4` | ... | ... |

## 3. 待业务 / 研发拍板的 Open Checks 汇总
1. `{章节}`：`{待确认问题}`

> 请确认需要我按上述建议修改的条目（可指定“全部修复”或仅勾选编号），确认后我再对正文执行修改。
```
