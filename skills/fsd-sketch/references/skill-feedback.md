# Skill 缺陷评估与脱敏反馈协议（低侵入 · 克制触发）

> **低侵入原则**：日常个案修改**完全静默**，绝不打断制图或自动调用 `gh` 提交。仅在用户**明确质疑/推翻 Skill 规则本身**时在回复最末附一句极短提示；用户主动要求或确认起草反馈时，执行本协议。

---

## 1. 先区分：个案修改 vs. Skill 缺陷

| 归因结论 | 判断标准 | 处理方式 |
|---|---|---|
| **个案修改（Case-Specific）** | 仅涉及当前页面的临时文案、单次构图偏好或特定客户定制例外 | 直接告知用户属于个案调整，**不建议提 Issue**。 |
| **Skill 缺陷（Skill-Level Gap）** | 反映出采集、重建、`sketchtool` API 或裁框规范本身的普遍性问题 | 按下方 4 类标签归因，生成**脱敏后的 Issue 草稿**交用户审阅。 |

### 四类 Skill 缺陷标签

| 标签 | 含义 | 典型示例 |
|---|---|---|
| `incomplete` | **写得不完整 / 漏场景** | 缺少某类浏览器框架、Sketch 版本兼容或导出避坑说明 |
| `mismatch` | **不适配当前场景** | 采集或布局重组流程不适用于某类新型界面组件 |
| `definition-issue` | **口径或原则有问题** | 脱敏数据规则、色彩转换或基线保留口径本身有误 |
| `too-rigid` | **过于死板 / 过度约束** | 强制步骤或裁框限制过死，导致正常界面还原受阻 |

---

## 2. 强制脱敏红线（提 Issue 前必须逐项过滤）

开源或跨团队共享仓库的 Issue **严禁包含任何客户或内部敏感信息**：
- ❌ 剥离真实客户名、项目代号、内部系统名与账号信息（替换为 `App A` / `User` 等泛化词）；
- ❌ 剥离内网 IP、内部域名、真实 URL、Cookie/Token、邮箱、人名；
- ❌ 剥离包含真实业务数据的截屏与 `.sketch` 源文件；
- ✅ 仅保留：**抽象后的界面/工具场景 + 命中了哪条现有规范 + 复现现象 + 建议如何修订**。

---

## 3. 标准 Issue 草稿模板

先输出以下草稿供用户审阅；**默认绝不自动执行外网提交**，仅在用户明确指令「帮我直接提 Issue」且当前环境具备 `gh` 权限时，再执行 `gh issue create --repo Starsaddict/FSD-skill ...`：

```markdown
### 标题
[fsd-sketch][<label>] <一句话概括规则问题>

### Labels
`fsd-sketch`, `<incomplete | mismatch | definition-issue | too-rigid>`

### 1. 涉及位置
- Skill / 文档：`skills/fsd-sketch/...`
- 相关章节或条款：`<章节名>`

### 2. 脱敏后的触发场景
<用泛化语言描述遇到了什么采集/绘制/导出场景，禁止出现客户名、内网地址或真实数据>

### 3. 问题分析
- 归因类别：`<写得不完整 | 不适配当前场景 | 口径有问题 | 过于死板>`
- 当前规则的不足：`<具体说明哪条规则导致了什么问题>`

### 4. 建议修订方向
<给出可落地的规则修改或补充建议>
```
