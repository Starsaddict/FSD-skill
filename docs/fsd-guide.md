# 功能规格说明书（FSD）标准范本与编写指南

> 本文档是面向产品、方案与研发团队的通用功能规格说明书（Functional Specification Document, FSD）编写标准与范本。文档结构与写法遵循平台无关原则，可直接用于 Markdown、飞书、Notion、Confluence、Word 等任意协作平台。

---

## 编写核心原则

开始编写任何 FSD 前，先对齐以下四条铁律：

1. **以 User Journey 为主线，而非技术分层**
   - 严禁把同一个用户操作拆散到“数据模型 / UI / 应用逻辑 / 流程图 / 校验 / 权限 / 接口”等孤立章节中。
   - 按用户进入并使用功能的真实路径展开说明；业务规则、状态转换、校验与错误处理**就地内嵌**在触发它们的功能节点中。
   - 同一个 Use Case（UC）包含多个独立 Feature 时，**每个 Feature 均遵循相同的路径骨架独立展开**。
2. **哪里用到才在哪里讲（Just-in-Time Context）**
   - 符合读者认知心智：先让读者理解“系统帮用户做什么、怎么用”，再讲背后的治理与配置。
   - 业务参与体（如 Digital Employees / 自动化执行角色）放在其所属业务总览的开头集中说明一次，后文不再重复切分。
   - 角色与权限矩阵（Access Control & User Roles）放在功能讲解之后的 **Configuration & Governance** 章节中统一说明。
3. **功能边界纯净（只写“做什么”，不写“代码怎么实现”）**
   - FSD 定义的是用户可见行为、业务契约、口径公式、状态规则与跨系统业务边界。
   - 明确移出 FSD 的工程/测试项（详见 [不纳入 FSD 的范围](#不纳入-fsd-的范围anti-scope)）：内部数据库表结构与字段长度、代码级类/钩子/插件扩展点、内部数据交换消息与内部 API 详细契约、数据迁移脚本、底层分析数仓模型、详细 QA Test Cases。
4. **组件级标准化表达 + 正文与制图分离**
   - 入口、Metric Cards、列表、表单、工作区、图表、固定章节报告、流程状态机、外部集成、权限、破坏性运维操作均使用固定模板，避免遗漏关键口径。
   - 写正文时不被截屏/画图打断：在视觉位先插入标准高亮块 Placeholder，正文定稿后再补图并替换。
   - **图文语言 100% 一致**：全英文 FSD 中的所有界面图、Sketch、流程图标签必须全英文；全中文 FSD 同理，严禁混杂。

## 不纳入 FSD 的范围（Anti-Scope）

以下内容归属技术设计文档（TDD / HLD / LLD）或测试计划（Test Plan），**不得写入 FSD**：

| 移出项 | 原因与归属 |
|---|---|
| 内部数据模型（DB 表名、字段类型/长度、索引） | 属于后端技术设计；FSD 只写用户可见的业务字段与业务规则。 |
| 功能扩展逻辑（代码扩展点、Hook、类名、插件内部方法） | 属于开发实现细节；FSD 只描述可配置规则与可见结果。 |
| 内部数据交换消息与内部 API 详细契约 | 仅当涉及**外部系统跨边界回调/状态同步**时，在对应功能节内描述业务级回调安全校验与状态映射，不罗列内部微服务接口。 |
| 数据迁移脚本与底层分析数仓模型 | 属于数据工程与实施交付文档。 |
| 详细 QA Test Cases / 单元测试步骤 | 属于测试计划与用例库，不占用 FSD 篇幅。 |

### 1 Background（背景与边界）

#### 1.1 Business background（业务背景）

##### Business scenario（业务场景）
- 用 1~2 段说清：当前业务痛点是什么？新功能/系统从整体上如何运作来解决该痛点？
- 避免写成空泛口号，需明确核心用户角色与高频作业场景。

##### Functional goals（功能目标）
- 用 3~5 条简洁、可验证的条目列明本期要达成的业务目标（例如：聚合降噪、证据化结论、自动闭环、可量化指标等）。

##### Scope of this phase（本期范围）
- 按核心能力分组，以精炼要点写明**本期包含什么**以及（必要时）**明确不包含什么**。
- **注意**：本节**不放置**阶段汇总表（如 `Business Stage | User Goal | System Responsibility`），所有阶段拆解统一归口至 `2.1.1 User Journey`，避免前后重复维护。

#### 1.2 Dependencies（依赖关系）

仅列明强依赖的外部平台、上下游系统、内置能力或前置配置：

| Dependency | Purpose |
|---|---|
| `{宿主应用 / 平台能力}` | `{提供什么承载能力或内置组件}` |
| `{外部系统 / 连接器}` | `{读取什么数据、触发什么动作或接收什么回调}` |

#### 1.3 Assumptions & Related Links（假设条件与相关链接，按需选填）

- 仅当方案成立依赖明确前提假设，或需要引用客户规范/外部产品说明时填写；无实质内容则省略本节。

### 2 Solution design（方案设计）

> **结构说明**：方案设计只分为两大主干——**2.1 Functionality（功能设计）**与 **2.2 Configuration & Governance（配置与权限治理）**。大屏看板、运营报表等专项用户界面在概念上均属于 `2.1 Functionality` 下的功能模块；仅当某独立交付面需单独拆分签收时，才可作为特例平级单列一节。

#### 2.1 Functionality（功能设计）

##### 2.1.1 User Journey（端到端用户旅程）

先建立读者的全局视角，串联跨角色、跨系统（及数字员工/自动化）的完整旅程：

1. **一句话导语**：概括该端到端旅程连接了哪些核心环节。
2. **端到端 User Journey 图**：插入泳道流程图（或 Placeholder），按编号阶段（`01 / 02 / 03 ...`）展示各参与角色/系统之间的交互流转。
3. **Journey Breakdown（唯一权威阶段拆解表）**：

| Stage | Primary Role | User Goal | Key Journey Activities & System Support |
|---|---|---|---|
| 1. `{阶段名称}` | `{主要角色}` | `{用户在该阶段的目标}` | `{关键动作与系统支撑要点，可引用对应章节}` |
| 2. `{阶段名称}` | `{主要角色}` | `{用户在该阶段的目标}` | `{关键动作与系统支撑要点}` |

##### 2.1.2 Feature N: `{功能名称}`（单 Case 多功能重复展开模板）

> 当一个 Use Case 包含多个功能模块（如核心工作台、运营分析报表、监控大屏等）时，**每个功能均按以下统一节奏展开**，不跳步、不把同一功能的逻辑切到别处。

1. **业务总览与参与体（Just-in-Time，按需）**
   - 用一段话说明本功能的定位与边界（尤其当存在容易混淆的相邻页面时，明确“这里看什么、和隔壁页有什么区别”）。
   - 若本业务域引入特殊系统参与体（例如多个 Digital Employees / 自动化代理），**在本业务总览开头用一张表集中定义职责**，后文不再重复切分：
     `| Actor / Digital Employee | Stage Owned | Core Responsibilities |`
2. **Entry Path（入口路径）**
   - 遵循 [组件模板 1：Entry Path](#1-entry-path入口导航)。
3. **按用户操作路径展开的界面与能力子节**
   - 遵循页面的自然阅读与操作动线（从上到下、从左到右、从列表到详情、从触发到闭环），选用对应的 [组件级写作模板](#组件级写作模板) 逐块编写。
   - **每个界面/模块必须先写 Purpose（让用户来看/做什么用）**，再放原型图，再给结构化表格与交互规则——切忌只罗列“页面里有哪些元素”却不说明用途。
   - **规则与异常就地内嵌**：支撑本功能的业务流程、计算口径、时间窗口、状态机、错误提示与外部系统回调，全部紧贴在对应功能节点中写清。

---

#### 2.2 Configuration & Governance（配置与权限治理）

所有面向管理员的配置、权限控制与运维保护统一收口在本章，符合“先懂业务功能，再看权限与后台配置”的读者心智。

##### 2.2.1 Access Control and User Roles（访问控制与用户角色）
- 遵循 [组件模板 10：Access Control and User Roles](#10-access-control-and-user-roles角色与权限矩阵)。
- 明确说明多租户/工作空间数据隔离边界（例如原始证据仅同空间已认证成员可见）。

##### 2.2.2 Settings Entry and Global Rules（配置入口与全局规则）
- 说明配置页入口（面包屑 + 截图）与角色可见性（如仅 Administrator / Workspace Owner 可见）。
- 用一张导航表列出全部配置菜单分组与用途：`Navigation Group | Menu Item | Purpose`。
- 写清**全局交互规则**：未保存变更提示与离开确认弹窗文案（如 `"Discard unsaved changes?"`）、放弃变更行为、保存后是否立即生效（无需单独发布步骤）。

##### 2.2.3 `{配置页 A / B / C}`
- 每个配置页面（数据源、外部系统集成、看板参数、定时任务等）按 [组件模板 4：Form & Settings Page](#4-form--settings-page表单--配置页) 的三段式结构编写。

##### 2.2.4 Maintenance and Destructive Operations（维护与破坏性操作，按需）
- 涉及数据重置、批量清理、不可逆删除等功能时，遵循 [组件模板 11：Maintenance & Destructive Operations](#11-maintenance--destructive-operations维护与破坏性操作)。

## 组件级写作模板

编写具体页面与功能模块时，按组件类型套用以下固定模板，确保口径完整、格式统一。

### 1. Entry Path（入口导航）
- **固定结构**：
  1. **面包屑导航路径**：`**平台 → 应用切换器（应用名）→ 左侧导航：功能名 → 顶部页签**`
  2. **入口标注截图**（带醒目红框标出目标点击项，或占位符）
  3. **默认落脚页与可见性说明**：进入后默认打开哪个页签/视图，顶部/右上角有哪些并列入口，哪些入口受角色权限隐藏。

### 2. Metric Cards（统计指标卡组）
> 术语统一称为 **Metric Cards**（不混用 Statistic Cards / KPI Cards）。

- **固定结构**：
  1. **定位说明**：说明卡片数量、排列位置，以及属于**纯展示**还是**可交互（点击切换下方图表 / 跳转来源报告）**。
  2. **原型图 / 占位符**
  3. **逐卡拆解表**（严禁把多张卡片揉成一段文字）：

| Card | Time / State Scope | Description, Formula & Empty-Value Rules |
|---|---|---|
| **`{卡片名}`** | `{Today / 7 days / Real-time snapshot}` | `{展示的主指标与副指标、精确计算公式、统计窗口归属规则、分母为 0 或缺值时的显示策略（默认留白不补零）}` |

  4. **卡片交互说明**（若有）：悬停提示（如展示公式与参数）、点击选中态及联动目标。

### 3. List & Table View（列表 / 工作队列）
- **固定结构**：
  1. **页面定位与入口**：说明本队列承载哪类对象，以及从何处进入。
  2. **列表原型图 / 占位符**
  3. **Field Specifications（列表列定义表）**：

| Field | Description & Business Rules |
|---|---|
| **`{列名}`** | `{字段业务含义、枚举值或格式限制（如字符上限）、折叠计数规则（如 +N）、排序/高亮规则}` |

  4. **List Controls & Navigation**：
     - 状态/分类页签（是否带计数）
     - 搜索框（支持按哪些字段检索）、筛选维度、排序选项、刷新与分页
     - **行点击目标（Row click destination）**：点击行后进入哪个详情视图或抽屉
     - 空态与加载失败提示。

### 4. Form & Settings Page（表单 / 配置页）
- **严格遵循三段式顺序**：**① 顶部状态与原型图 → ② 表单项定义表 → ③ 表单交互与校验规则**。
  1. **① 顶部运行时状态与操作区 + 表单原型图**：
     - 若表单顶部有状态徽标（如 Running / Stopped）、最近执行统计、独立启停开关（Pull）、只读试跑按钮（Trial read）或更多菜单，先写清其展示与行为；紧接着给出完整表单原型图。
  2. **② 表单项定义表（固定列）**：
     - 扁平表单使用 2~3 列；若表单内部包含多个分组卡片，建议用小标题分段，或按需增加 `Group` 列。

| Field | Description & Constraints | Example / Note（可选） |
|---|---|---|
| **`{表单项名}`** | `{控件类型（输入/下拉/开关/多选等）、是否必填与默认值、取值范围、业务含义、显隐/只读/级联依赖条件（如先选 Connector 才展示 Skill 列表）、校验规则与阻断提示文案}` | `{示例值、客户占位符说明或 [Open Check]}` |

  3. **③ 表单交互与生命周期规则**：
     - 试跑 / 预览行为（明确是否只读、是否落库、是否推进游标）
     - 保存生效时机（立即生效 vs 需手动发布）、修改游标/关键参数时的提示
     - 未保存变更保护与离开拦截文案
     - 删除/禁用等操作对已有历史数据的影响边界。

### 5. Detail Workspace & Tabs（分栏 / 多 Tab 工作区）
- **固定 4 步自顶向下结构（操作随区走，不把操作流放到文末）**：
  1. **Workspace Purpose & Entry**：一句话说明工作区解决什么核心任务 + 从何处点击进入 + 打开时的加载行为（如仅渲染最新已保存状态，不触发新计算）。
  2. **Full Layout Visual + Zone Map**：先贴完整工作区原型图，紧跟区域地图表：

| Zone | Purpose（让用户来看/做什么） | Key Interactions（核心交互） |
|---|---|---|
| **Left Pane — `{区名}`** | `{该区核心用途}` | `{该区支持的输入/对话/点击动作}` |
| **Right Pane — `{区名}`** | `{该区核心用途}` | `{页签切换、按钮操作、缩放等}` |

  3. **Zone-by-Zone Breakdown（按主操作区 → 辅助区，或左 → 右逐区展开）**：
     - **交互/对话区**：在本区内直接写清展示内容 + **用户可发起的操作表**（`Operation | Trigger / Entry | Execution & Side-Effect Rules`）。
     - **多 Tab 详情区**：按 Tab 逐个展开，每个 Tab 固定遵循：`Tab Purpose（先讲让用户看什么） → 局部原型图 → 字段/模块定义表 → 本 Tab 独有控件与顶部操作按钮`。
  4. **Cross-Zone Sync & Exception Rules**：集中收口跨区联动（如左区指令如何触发右区刷新、失败时保留上次成功快照）、并发处理锁（处理中再次发送如何提示）、以及加载失败报错文案。

### 6. Analytical Charts（分析 / 趋势图表）
- **固定结构**：
  1. **Purpose & Entry**：图表解决什么分析问题 + 默认展示还是通过点击哪张 Metric Card / 页签切换进入。
  2. **图表原型图 / 占位符**
  3. **规格说明**：
     - 统计周期与时间轴边界（如近 7 天 / 近 30 天 / 本月至今，横轴截止点）
     - 系列定义、计算公式与参考基线（Mean / Median / Baseline）
     - 头部汇总条（如有）与对应 Metric Card 的一致性规则
     - **空值与缺日期处理**：明确缺失日期/无数据时留白，绝不以 0 填充
     - 交互模式（纯展示 vs Hover 提示 vs 下钻）。

### 7. Report / Generated Document（报告 / 生成式文档）
- **固定结构**（适用于定时周报、专项分析报告、审计报告等具有固定章节骨架的报告产物）：
  1. **Report Purpose, Trigger & Scope**：报告面向谁、解决什么复盘/分析目标、触发方式（手动 / 定时调度）、统计观察窗口（Lookback / Reporting period）、输出格式（如完整 Markdown 文档）以及生成中是否支持取消。
  2. **Entry & Preview Visual**：说明从何处进入报告详情或工作区（列表行点击 / Metric Card 来源链接 / 手动触发）+ 报告展示界面原型图（若采用左对话+右报告分栏工作区，结合模板 5 说明区域与交互）。
  3. **Fixed Report Structure（固定报告章节规格表 — 核心必填）**：逐章写清该类报告的统一章节名称与每章固定讲述的内容、数据口径及对比维度（如周报相对常规分析报告额外包含的环比对比与下期重点）：

| Section / Chapter | Purpose & Fixed Content | Data Scope & Integrity Rules |
|---|---|---|
| **1. `{固定章节名，如 Operational Conclusion}`** | `{本章节固定讲什么结论或核心洞察}` | `{数据窗口、引用的关键指标或证据边界}` |
| **2. `{固定章节名，如 Observation Scope & Coverage}`** | `{固定说明观察时间窗、时钟口径与采集覆盖范围}` | `{缺口与未覆盖对象如何如实披露}` |
| **3. `{固定章节名，如 Key Metrics / Trend / Recommendations}`** | `{按实际固定章节依次完整列出}` | `{缺值留白不补零、不估算代理指标、不将相关性表述为因果}` |

  4. **Post-Save Sync, Follow-up Q&A & Failure Handling**：
     - **保存后联动**：报告成功保存后是否同步刷新概览页的摘要条、Metric Cards 与图表。
     - **只读与追问边界**：用户基于已保存报告发起追问时，回答必须严格受限于该报告与对应观察窗口，**绝不修改或覆盖已保存的历史报告**。
     - **异常与取消**：生成失败/保存失败的状态与错误提示（未保存完成绝不宣称成功）、生成中取消及取消失败的提示文案。

### 8. Process Flow & State Machine（业务流程、时间窗口与状态机）
- **固定结构**：
  1. **触发条件与定位**：由什么事件/定时任务/人工操作触发，覆盖什么处理范围。
  2. **流程图 / 状态迁移图（或 Placeholder）**
  3. **分步规则与分支说明**：
     - 主路径步骤 + 判定条件表
     - 失败/异常分支（明确游标是否推进、是否保留原始载荷、谁可重试、重试失败如何记录）
     - **时间窗口与边界规则表**（涉及多个计时器时必须写明是否独立、是否重置、到期后去向与是否通知）：
       `| Time Rule | Default | Boundary & Reset Behavior |`
     - **状态迁移与终止路径**：列明全部合法状态、每条终止路径的触发条件、是否不可逆、以及对关联对象/外部系统的联动影响。

### 9. External Integration & Callback（外部系统集成与回调）
- **固定结构**：
  1. **触发条件与业务字段映射**：何时触发外部创建/更新/关闭、关键业务字段映射（不写底层 DTO 字段名，只写业务语义）、单对象并发上限（如至多一个进行中工单）、超时与未确认防重规则。
  2. **唯一权威状态映射表**（全文档所有页面与看板必须共用此表，严禁出现两套口径）：

| Status | Source | Meaning & Rules |
|---|---|---|
| **`{展示状态}`** | `{本系统 / 外部系统状态码}` | `{业务含义、是否计入已认领/已关闭、异常保持规则}` |

  3. **回调与安全校验表**（若接收外部回调）：
     `| Validation Check | Rule |`（至少覆盖：调用方身份鉴权、状态真实来源防伪造、对象归属校验、非法参数拒绝、外部读取失败降级、允许更新的最小字段范围）。

### 10. Access Control and User Roles（角色与权限矩阵）
- **固定结构**：说明数据可见边界（工作空间/租户隔离）+ 角色权限矩阵表：

| Role | Access Scope | Allowed Capabilities |
|---|---|---|
| **`{角色名}`** | `{可访问的功能页与数据范围}` | `{允许的只读/操作/配置/治理能力，明确禁止的关键操作}` |

### 11. Maintenance & Destructive Operations（维护与破坏性操作）
- **固定结构**：
  1. **入口与原型图 / 占位符**
  2. **影响范围表**：

| Group | Affected Data & Behavior |
|---|---|
| **Clears（清理内容）** | `{会被永久删除的数据类别}` |
| **Keeps（保留内容）** | `{不受影响、完整保留的配置与规则}` |
| **Post-action Behavior（执行后恢复行为）** | `{已启用任务/数据源如何重新启动及起始游标位置}` |

  3. **安全护栏**：二次确认弹窗、执行结果反馈（删除条数等）、以及生产环境防误操作措施（禁用 / 执行前导出 / 双人审批 / 审计日志；若待拍板则标 `*[Open Check: ...]*`）。

## 定稿前核心自检要点

文档交付评审前，必须确认以下底线已全部满足（完整分级清单见 `skills/fsd-writer/references/qa-checklist.md`）：

1. **目录与正文 100% 同步**，无空壳章节，无重复描述。
2. **所有状态枚举全篇唯一**：列表、详情页、Dashboard 与外部系统映射使用完全一致的状态词。
3. **跨系统联动闭环**：人工关闭、规则关闭、超时过期对外部工单/关联对象的影响各自写清，无模糊地带。
4. **每个页面/Tab 先写 Purpose，再写内容**，且明确 Entry Path 与相邻视图边界。
5. **计算口径完整**：每个指标写清公式、统计窗口、时间归属字段、分母为 0 / 缺值留白规则，以及客户基线参数的可配置性。
6. **高危操作有护栏**：清理/重置/删除写清清理范围、保留范围、二次确认与生产防护。
7. **无开发实现与测试用例泄漏**：无内部表结构、代码类名、内部 API 细则或 QA 用例。
8. **图文语言 100% 一致**，所有 `VISUAL-PLACEHOLDER` 已补图替换，所有待业务拍板事项均已显式标出 `*[Open Check: ...]*`。
